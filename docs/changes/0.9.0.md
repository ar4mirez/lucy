# 0.9.0 (2026-11-28)

Converge loops, merge postures from the spec, and Pilots that start the same way every time
(milestone m1: slices 7b and 8). The daemon's background work now runs as converge loops woken by
the event log, so the Tower reacts when a commit lands rather than on its next poll, a failing
flight backs off on its own, and a Pilot that cannot start during an outage is retried instead of
grounded. A project's merge posture can come from the spec's AutonomyPolicy, through its Runway:
a demotion tightens flights already in flight, a promotion applies only to later ones, and
`lucy config reload` (or SIGHUP) applies either without a restart. Only you can override a
QualityGate.

Before every spawn the runner now re-asserts the harness's account state in the org's synthetic
home, installs and verifies lucy's own bundled skills there, and, when that home has no login for
the harness, holds the run for you with a question instead of starting a session that would wait
on a login prompt for ever.

Limits, plainly:

- **lucy is still in shadow mode.** The Tower's forge is a stub that merges nothing until the
  validation slice, and no Flight is dispatched onto a real repository until runs get an OS
  boundary of their own (#36) and the owner's go/no-go.
- **A Pilot on this machine still shares the daemon's user** and so its API authority for its own
  org (#36).
- **Container placement still waits on berth** (berth#216).
- **Skills stay off in Pilot sessions** until a live check of the harness shows a skill cannot
  skip a permission prompt and a repository's own skills do not load; a Pilot gets its role's
  instructions in lucy's system prompt meanwhile.
- **A reload does not refresh everything:** the roles' blocked paths and the gateway's routes still
  take a restart.

**Upgrading from 0.8.0:** follow [the upgrade runbook](../runbooks/upgrade.md): drain each 0.8.0
runner with `lucy runner drain --org <org>` and start a 0.9.0 one in its place. A 0.9.0 runner
holds a run for you when its org's synthetic home has no login for the harness, so log in once as
that home (for Claude Code, run `claude` with `HOME` set to the runner's `--root` followed by
`/home`) before relying on it; the first run there tells you so otherwise.

Install it with `mise use -g github:ar4mirez/lucy@0.9.0`, then check it with `lucy --version`.

### Added

- Only you can override a QualityGate. A gate whose `override.requiredRole` (or a visual rule whose
  `override.approvers`) names anyone else is still loaded, as the spec writes it, but `lucy config
  status` shows the condition `Override` (`OverrideIsOwner`) saying lucy lets only you override
  it, and the daemon logs a warning. Its `requiresJustification` is kept.

- `lucy config reload` (the API's `config.reload`, OpenRPC revision 21) and SIGHUP make the daemon
  load its config again without a restart. A config with no refused resource is applied: its
  statuses are recorded, its new Ready Flights dispatched (with `--dispatch`), its flights in flight
  tightened. A config with refused resources is not applied, and the command lists why, but its
  strictening still applies: a flight whose Runway or AutonomyPolicy became invalid or vanished
  moves to owner. A config directory that cannot be read, or no longer exists, fails the reload:
  the last good config stays whole, no flight is tightened, `daemon.config_reload_failed` records
  why, and `lucy config status` shows the last reload that failed or was refused. A loosening never
  applies to a flight in flight. The roles' blocked paths and the
  gateway's routes still take a restart.

- Demoting a Runway's autonomy level now tightens its flights already in flight, on `lucy config
  reload`, SIGHUP or the next start: each moves to the stricter posture, recorded as `task.posture_tightened` with the old
  and new posture and why, and its next merge is decided again under it. A promotion applies only
  to Flights dispatched afterwards, never to one in flight. A flight whose posture can no longer be
  resolved from the config moves to owner (a client flight stays client): its Runway is removed or
  refused, its Runway's AutonomyPolicy is removed or has a field lucy refuses, or neither its Runway
  nor its Flight states a posture any more.

- A project's merge posture can come from the spec's AutonomyPolicy: a Runway names a policy and a
  level (`autonomyPolicy`, `autonomyLevel`), and lucy reads only that level's
  `guardrails.requireApproval`: `all` is the owner posture, `security-critical-only` the green
  posture, with the fixed list still needing you; `none` and `architecture-changes-only` are
  refused. `clientConfirms: true` on a Runway adds the client's confirmation, relayed by you. A
  Flight no longer needs its own `autonomy` when its Runway sets one, and its own may only tighten
  it. Every other field of a policy a Runway names is refused by name, and a Flight whose posture
  cannot be set is held with reason `AutonomyInvalid`. Promotion and demotion stay yours, by hand.
  `flights.list` reports the posture a Flight is flown under (OpenRPC revision 20).

### Changed

- lucy bundles its own skills, one per Pilot role, each with its SHA-256 in a manifest. Before
  every spawn the runner installs them into the harness's skills directory in the org's synthetic
  home, verifies each against the manifest, and removes anything else there, through the path
  guard; a mismatch refuses the spawn. Only lucy's skills are ever installed. Sessions still run
  with skills switched off until a live check of the harness shows they cannot skip a permission
  prompt; a Pilot gets its role's instructions, from the same bundle, in lucy's system prompt,
  before the repository's instructions.

- A Pilot whose harness has no login in its org's synthetic home is held for you instead of
  wedged on a login prompt: the runner does not start it and finishes the run `needs_owner`
  (`runner.finish`, OpenRPC revision 22), and the Tower asks you, in its own words, where and how to
  log in once as that home. The question never asks for a secret, and lucy reads no login and
  copies none from your home; no timeout grounds the flight while it waits, and your answer
  (`lucy answer <flight> done`) starts the Pilot again.

- Before every spawn, the runner re-asserts the harness's account state in the org's synthetic
  home: for Claude Code, onboarding complete, the run's directory trusted with no tools pre-allowed,
  no MCP servers, auto-updates off, no hooks. It writes only inside that home, through a guarded
  root, keeps every other key (the login among them), never reads your own home, and refuses the
  spawn when a file it would write there is a symlink or not a JSON object.

- A Pilot that cannot start during an outage no longer grounds its flight: the failed start is
  recorded (`task.pilot_start_failed`) and retried after a backoff that doubles with each failure,
  and `lucy flights` shows why and when it is tried next. Only a start the runner protocol refuses
  for good (an invalid task, a run id another flight holds, an older generation) still grounds the
  flight with `start_failed`.

- The daemon's background work runs as converge loops woken by the event log: the Tower steps its
  flights as soon as a commit lands (a Pilot's question reaches `lucy questions` within a second of
  the runner's heartbeat, not on the next poll), still polls while a flight is active for what the
  log does not carry, and backs off a flight whose step fails, that flight alone, instead of
  retrying it on every poll; `flights.list` shows its `step_error` and `retry_at` (OpenRPC
  revision 19). Lease expiry runs the same way, so a finished run's capability token is revoked
  when the run's end is recorded, not on the next sweep, and still revoked when an expiry fails.
